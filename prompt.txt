ENGINEERING PRINCIPLES
==================================================

Use:

- TypeScript strict mode
- pnpm
- Turborepo
- Next.js
- NestJS
- Fastify
- PostgreSQL

- Redis
- BullMQ
- Tauri 2
- React

- shadcn/ui
- pgvector
- OpenTelemetry where appropriate

Use a MODULAR MONOLITH + WORKERS architecture.

Do NOT create unnecessary microservices.

Keep clear domain boundaries.

Use dependency injection.

Keep controllers thin.

Put business logic in services/use-cases.

Put persistence behind repositories/services where appropriate.

==================================================
SECURITY IS NOT OPTIONAL
==================================================

Every feature must consider:

- authentication
- authorization
- tenant isolation
- input validation
- rate limiting
- secret handling
- PII protection
- audit logging
- idempotency
- SSRF
- prompt injection
- webhook verification
- CSRF where applicable
- secure cookies
- CORS
- security headers

Never trust:

- client-provided merchant_id
- client-provided payment status
- LLM output
- merchant website content
- browser events
- external webhook payloads

All sensitive operations must be validated server-side.

==================================================
MULTI-TENANCY
==================================================

RAY is multi-tenant.

Merchant A must NEVER be able to access:

- Merchant B's products
- Merchant B's customers
- Merchant B's orders
- Merchant B's conversations
- Merchant B's events
- Merchant B's integrations
- Merchant B's payments

Never rely on frontend filtering for tenant isolation.

Tenant authorization must happen in the backend.

==================================================
PAYMENTS
==================================================

Razorpay is the payment authority.

Never mark an order as paid because:

- frontend says payment succeeded
- AI says payment succeeded
- browser callback says payment succeeded

Payment state must be verified server-side.

Razorpay webhooks must:

1. receive raw body
2. verify signature
3. deduplicate
4. persist event
5. acknowledge quickly
6. process asynchronously
7. update payment/order state safely

==================================================
AI
==================================================

LLMs are NOT trusted systems.

LLMs can request tools but cannot directly perform privileged operations.

Architecture:

LLM
 ↓
Tool Request
 ↓
Validation
 ↓
Authorization
 ↓
Policy Engine
 ↓
Domain Service
 ↓
Database/external integration

Never allow an LLM to bypass business rules.

Never put secrets into prompts.

Never expose unnecessary PII to LLMs.

Merchant website content and customer messages are UNTRUSTED DATA.

==================================================
MCP
==================================================

MCP must use the same underlying domain services as REST/API.

Do NOT duplicate business logic inside MCP.

MCP tools must be:

- authenticated
- tenant-aware
- validated
- authorized
- rate limited
- audited
- timeout protected

==================================================
DATABASE
==================================================

PostgreSQL is the source of truth.

Do not use:

- frontend state
- Redis
- vector database
- desktop local storage

as the authoritative business database.

Use PostgreSQL for transactional state.

Use Redis for caching/queues.

Use pgvector for semantic search.

==================================================
NO FAKE CORE LOGIC
==================================================

Do NOT create fake hardcoded logic such as:

products = [
  { name: "Nike Shoe", price: 4999 }
]

for production application flows.

Use the actual database.

Seed data may be created for development/testing, but it must enter through the real data model.
